## 5. 与「现状」不符的地方（逐条带证据）

### 5.1 补丁不完整：`manifest.json` 的变更没有进 diff
`docs/r06-patch.diff` 只有 1 个 `diff --git` 段（`ext/abc/index.js`）。而 `HANDOFF.md` 的 I6 表登记了 `manifest.json` 改前 `43a5d859…` / 128 B → 改后 `b6eb5659…` / 132 B。设备确实是改后版，但**这个改动无补丁可复现**。执行 P0 时 `git apply` 完，`manifest.json` 仍是 `1.0.0` / 128 B，与登记不符。

### 5.2 版本标识四分裂
`v1.0.0` tag → 仓库 `manifest.version = "1.0.0"` → 补丁里 `EXT_VERSION = '0.5.1-r04'` → 设备 `manifest.version = "0.5.1-r04"`。即：**打了补丁的仓库会自称 0.5.1-r04，而未打补丁的仓库自称 1.0.0**，同一份代码两个版本号。接手者无法从版本号判断跑的是什么。

### 5.3 `HANDOFF.md` 的补丁统计口径对不上
`HANDOFF.md` 写「改动仅 28 增 4 删」；diff 实测 **+24 / −3**（3 个 hunk，不含文件头）。差 4 行，属统计口径，但会让核对者以为漏了内容。

### 5.4 「压缩失败 = 网关 503」这条判断已过期
按日期统计宿主日志（本地字节保真后重扫；**先前用 `adb shell grep -c` 得到的计数不可信，Android toybox 与管道转义会污染结果，必须在本地重扫**）：

| 日期 | `disk overloaded` / 503 | `Could not establish a secure connection` | `JSONL payload is not valid UTF-8` |
|---|---|---|---|
| 10-26 | 0 | 3 | 0 |
| 10-28 | 0 | 0 | 0 |
| 11-01 | 0 | 1 | 0 |
| 11-02 | **4** | 0 | 0 |
| 11-03 | 0 | **22** | 0 |
| 11-04 | 0 | 4 | **1** |

结论：503 只集中在 11-02（与 findings §2.6 一致）；**11-03 之后的上游故障换成了 TLS 连接失败**（`…/v1/models`，`GATEWAY_HOST`），11-04 20:34:35 又出现一类全新的失败。

### 5.5 新的失败形态：宿主拒绝启动 run（`start_failed`）
`[CHAT_A]` 的 `compEvidence` 最后一条：

```
outcome = "start_failed"
from/to = 131/134     msgs = 2     sysChars = 796     runId = null
error   = "Bad request: JSONL payload is not valid UTF-8: incomplete utf-8 byte sequence from index 75349"
```

宿主日志同一时刻（UTC 12:34:35.444084 = 北京 20:34:35）：

```
ERROR tauritavern::user_error: Failed to start agent run: Validation error:
      JSONL payload is not valid UTF-8: incomplete utf-8 byte sequence from index 75349
```

已排除的两个方向：
* **聊天文件本身没有坏**：`[CHAT_A]` 的 jsonl（3,711,641 B）严格 UTF-8 解码 **0 错误**；全聊天 **0 个 U+FFFD、0 个孤立代理、0 个非 BMP 字符**。
* **不是 abc 的字符串截断**：`rangeText()` 不做切片（`index.js:99`），扩展内所有 `.slice()` 都作用在数组或 ≤200 字符的日志字段上（`index.js:96/185/211/214/255/409`）；压缩范围 131–134 楼的原文合计约 3,676 字符（≈11 KB），远小于 75,349 字节的失败偏移。

未定性：payload 是宿主组装并校验的（`initialChatHistoryMessages: -1` → 全量历史进 payload），75349 是 payload 内偏移，失败发生在 **run 创建之前**，扩展没有接管点。**这条要归到「宿主/上游」，但在拿到 payload 落盘证据前不定死。**

### 5.6 `compEvidence` 出现了文档没记的 outcome
`tech-notes.md` §4.4 写「`outcome` 应走 `pending → started → applied | discarded`」。实测还有两种：

* `start_failed`（见 5.5）——`index.js:409`，`compress_start_failed` 事件，`runId=null`。
* 停在 `started` 且**没有终态**的 1 条（`from/to = 25/28`，`runId=run_2984b57c…`）——即 §4.4 说的「压缩 run 丢了终态事件」，本样本有实证。

### 5.7 `discardReason` 混了两种语义
`index.js:435`：`evD.discardReason = mismatch || ev.type`。所以 `run_completed` 这个值不是「网络失败」，而是**压缩 run 正常结束、但没暂存 chronicle**（模型没按协议调 `chronicle_commit`）。本样本 `discarded` 3 条：`run_completed` ×2、`run_failed` ×1。**排查时把 `run_completed` 当成上游故障会走错方向。**

### 5.8 压缩比文档更慢
`debug` 里 `compress_run_started` → `compress_run_terminal` 按 runId 配对，35 次有效样本：

```
min 7.8 s | median 53.4 s | mean 49.4 s | max 90.7 s | 7 次 ≥ 60 s
```

`tech-notes.md` §1-P4 记 22–51 s，`HANDOFF.md` 记 40–60 s。**最大值已到 90.7 s。**

### 5.9 轮询空转量级比文档大一个数量级
`tech-notes.md` / findings 记「约 300 次扫描命中 1 次」。本样本 `discover_skip_not_main` 的 `count` 字段（R05 遗留的历史累计）为 **8006**；补丁的单槽 `n` 为 **36**（`slot = "discover_skip_not_main|"`，`n` 字段存在 → 确认归并逻辑在真机生效）。两个数是不同口径，**报告时必须分开写**，否则会被读成互相矛盾。

### 5.10 `chronicle` 不是数组
`index.js:38` 初始化 `chronicle: ''`，`:453` 覆盖写入，`:456` 才 push 进 `compLog`。所以「chronicle 条数」这个说法会误导：它是**一份累积全文**（本样本 8,146 字符），累计次数要看 `compLog`（32 条）或 `compEvidence.applied`（32）。

### 5.11 设备多一个过期文档
`ext/abc/README.md`（2,924 B，2026-10-24）是 v0.2.1 时期的说明，里面还写着 `state_propose`、守卫、白名单裁定、`extra.abc_state`——**全是 v0.5 已剥离的变量层**。仓库无此文件。任何人读到它都会以为变量层还在。
